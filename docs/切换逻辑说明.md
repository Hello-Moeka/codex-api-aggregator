# 聚合 API 切换逻辑说明

适用版本：2026-10-17 开源审计修复版。下文描述自建路由器的规则；网关与供应商内部的调度无法由此控制。

## 1. 默认顺序与选路入口

默认按 `control-settings.json` 的 `sources` 顺序选择，例如：Plus A → Plus B → Provider A → Provider B。面板调整排序后，以实际配置为准；发行版不附带供应商账号或真实渠道配置。

普通模型名，例如 `gpt-6.1-sol`，会筛选提供该模型的来源，再根据会话保持、官方接管和低价回迁规则排列候选。暂停、额度不足、预留保护或熔断未到期的来源会被跳过。模型名使用上游原名；不同名称不会自动视为同一个模型。

带来源前缀，例如 `provider-a/gpt-6.1-sol`，表示只请求该来源。即使失败也不会切到其他来源。客户端若一直使用带前缀的模型，就不会发生跨来源故障转移。

## 2. 单次请求如何故障转移

每个候选来源在一次请求中最多尝试一次。在尚未向客户端发送生成内容、推理增量或工具调用事件时，上游网络错误、超时、5xx、协议错误、限流、额度或模型不可用，可以继续尝试后续候选。

参数错误或上下文超限会停止继续尝试；客户端取消会停止上游请求。所有候选均不可用时返回错误，日志记录每一步的尝试或跳过原因。

“本次失败后切下一家”和“进入熔断”是两个判断。单次 502 或等待有效事件超时，即使没有达到熔断阈值，本次请求仍会尝试下一家；下次请求是否跳过它，由状态决定。

一旦生成内容、推理增量或工具事件已经发给客户端，就不自动回放到其他来源，以免重复输出或重复执行工具。流中断后，客户端需要处理错误或重新发起请求；已输出的流不会被拼接到另一个来源。

## 3. 会话保持与主动回迁

客户端通过 `session_id`、`x-session-id`、`conversation_id` 请求头或 `prompt_cache_key` 提供会话标识。开启会话保持时，成功来源成为该会话的优先来源。没有这些标识的请求，无法享受会话保持和对应的 30 分钟计时。

绑定闲置 1 小时失效，最多保存 5000 条。计时从成功切换来源时开始，同一来源的后续成功请求不会重置计时。较早发起但较晚完成的请求，不会覆盖较新请求已经建立的绑定。

### 官方恢复接管

当前会话使用中转站时，如果 Plus A/B 支持所请求模型、已启用、额度和预留校验通过、来源与模型状态健康，则在下一次请求优先尝试官方。该规则不受中转站 30 分钟保持限制，当前正在生成的请求不会中途迁移。

两者都符合时优先 Plus A。若当前已稳定绑定 Plus B，Plus A 恢复不会主动抢占健康的 Plus B；B 不可用后才重新回退选择。

### 中转站低价回迁

当前中转站成功绑定满 30 分钟后，才主动考虑排序更靠前的中转站。目标必须通过恢复流程、对应模型有成功记录，而且来源和模型均无未解决故障。

故障恢复通常需要两次成功验证，两次间隔至少约 15 秒；之后进入默认 5 分钟观察期。观察结束还需额外一次实际探测成功，才有资格接管旧会话。30 分钟保持与观察期可以同时计时，并非一定先等 30 分钟再等 5 分钟。

多个目标都符合时选排序最靠前的目标。回迁只在下一请求边界发生。当前渠道一旦失败，会立即回退，不需要等满 30 分钟。

观察未通过，或实际回迁后的 30 分钟内再次失败，会重新熔断，并将后续回迁观察期提高到 10、20、30 分钟，最高 30 分钟。普通熔断冷却与回迁观察期是两套计时。当前实现不会自动把提高后的观察期降回 5 分钟。

举例：03 失败后会话改用 04。03 经两次验证恢复，再经过 5 分钟观察及额外验证；如果 04 尚未保持满 30 分钟，继续使用 04。两个条件都满足后，下次请求优先 03。期间官方恢复，则下次请求可优先官方。

## 4. 故障状态与隔离范围

| 情况 | 处理与恢复 |
| --- | --- |
| 普通网络、5xx、协议或超时错误 | 连续 3 次失败，或最近 10 次结果至少 6 次失败，进入熔断；未达到阈值时下次请求可重试，同时约 30 秒后安排后台恢复检查 |
| 熔断 open | 冷却约 30、60、120、300、600、900 秒逐级延长，带 ±10% 抖动；冷却结束安排验证 |
| 验证 half_open | 同一故障范围同时只允许一个验证者；两次成功后恢复 closed，失败重新冷却 |
| 429 限流 | 立即等待 `Retry-After`；缺失或不可解析时默认约 60 秒 |
| 模型不存在、无渠道或无权限 | 立即隔离该来源下的这个模型；其他模型仍可使用 |
| 来源级网络、协议或认证问题 | 可影响整个来源，不只一个模型 |
| 官方额度耗尽 | 等待实际额度查询确认恢复；预计重置时间到了不会直接解除 |
| 中转余额耗尽 | 等待较新的正常余额查询结果，再转入实际恢复验证 |
| 认证失效 | 需更新凭据或重新授权；中转站可手动检查恢复触发验证，官方额度查询正常后仍需实际请求验证 |
| 手动暂停 | 不参与请求和自动恢复探测；先手动启用 |

closed 仅表示没有熔断拦截，不保证上游必然正常。显示“请求异常，未进入熔断”是允许存在的状态。

恢复探测和业务流使用相同的协议解析，不能仅凭 HTTP 200、握手事件或 HTML 页面判断成功。恢复成功后清除旧的滚动失败历史，避免刚恢复就被历史记录立即再次熔断。并发旧请求的成功也不能清掉较新故障。

## 5. 官方预留 10% 与窗口恢复

预留开启时，短窗口或周窗口任一个已用达到 90%，就跳过该官方账号；刚好剩 10% 也会跳过。两个窗口均恢复到预留线以上，才可重新选用。额度未知或查询失败时保护性跳过。

后台通常每 60 秒查一次官方额度；业务请求会补查，同账号 15 秒内复用结果，避免并发重复查询。关闭预留时后台通常每 300 秒检查，实际额度耗尽仍不能绕过。

系统会检查实际使用情况，因此能够识别提前恢复，不会死等原来的 5 小时或周重置时间。正常额度查询只解除额度限制，不能同时清除网络熔断、认证故障或失败计数。

预留是基于最近查询值的请求准入保护，不是精确的 token 硬限额。一个已开始的大请求或多个并发请求仍可能消耗超过剩余安全空间。

## 6. 等待时间

| 限制 | 普通请求 | 高推理请求（high/xhigh/max/ultra） |
| --- | --- | --- |
| 输出前整条候选链预算 | 180 秒 | 600 秒 |
| 等待首个有效事件 | 60 秒 | 120 秒 |
| 有握手但尚无生成进展 | 最多约 180 秒，同时受剩余链预算限制 | 最多约 360 秒，同时受剩余链预算限制 |
| 已输出后的无进展超时 | 120 秒 | 300 秒 |

持续生成中的流不会因为输出前预算到期被截断。上述时间还包含网络与调度开销，不代表每家都能拿到完整等待时间。后台恢复探测总时限约 60 秒，手动测试子进程也有 60 秒总时限。

## 7. 续接请求的特殊限制

携带 `previous_response_id` 的请求只能回到生成该 ID 的原来源，不跨渠道，不受主动回迁覆盖。这类 ID 通常不能在不同账号或中转站间通用。

映射未知或超过 1 小时，返回 HTTP 409 `continuation_requires_full_history`。客户端需改为发送完整历史后重新建立请求。路由器不会自动从 ID 还原历史，也不会自行改写会话。

## 8. 面板按钮与记录含义

| 操作或记录 | 实际功能 |
| --- | --- |
| 一键全部测试 | 用所选的同一个模型逐来源发送真实定向生成请求，最多并发 2 个；暂停、未提供该模型或被准入规则拦截的项目记跳过；不代表所有模型都测试过 |
| 每行“测试” | 用该来源所选模型发送定向生成请求，要求完成且文本包含 `GATEWAY_OK`；遵守熔断和额度规则，不能强行穿透 |
| 检查恢复 | 安排恢复检查；中转站先更新余额；可以提前当前熔断的验证时间，但不能绕过暂停、余额或官方预留保护，也不能跳过尚未结束的回迁观察期 |
| 刷新余额 | 查询供应商余额，不执行模型生成；正常余额并不代表模型可用 |
| 同步上游模型 | 手动读取上游目录；中转站目录不自动定时同步 |
| 最近恢复探测 | 后台或手动恢复检查的实际验证结果，含模型、时间、结果和错误类别 |
| 最近手动测试 | 单行测试或全部测试留下的历史记录，不直接代表当前可用性 |
| 请求日志 | 记录经路由 API 的请求结果、来源尝试与跳过原因、耗时和 token 统计；不保存请求正文、原始上游错误正文、账号令牌或会话标识 |

恢复验证只证明被测模型在该时刻能完成响应，并不保证所有模型或工具能力均正常。后台恢复使用短文本 `Reply OK.`；一键测试使用短文本标记，二者目的不同，因此可能出现恢复成功但后来手动测试失败。

## 9. 重启与使用边界

故障状态、额度与探测记录落盘；会话绑定和响应 ID 映射仅在进程内。路由器重启后，30 分钟会话保持重新建立，旧 `previous_response_id` 可能需要完整历史重新发起。

健康检查、余额查询、模拟测试通过，都不等于真实供应商持续稳定。本轮验证采用本地模拟上游，没有为审计向真实供应商发送付费生成请求。
